## 项目整体审查（Server + Web 设计思想梳理）

通读全项目（2304 行 TS：common 3 文件 / server 3 文件 / Web 6 文件），评估架构设计。
版本管理用 jj，提交历史 1 天多，commit message 质量高（都写了决策原因）。

### 架构理解（已确认的设计思想）

- **GitHub 模型**：房间 = 仓库，加入 = pull 覆盖本地，新建 = 建仓 + push；本地数据非权威
- **双密码**：joinPwd（读，可空 = 公开房间）+ gmPwd（写，≥6 位），读写权限分离
- **单写者假设 + 乐观锁兜底**：GM 写玩家读，version 冲突返 409 + 最新状态，客户端整体替换（丢包重做）
- **全量覆盖而非增量**：数据几 KB，无 diff/合并复杂度
- **common/ 为共享纯函数层**：几何（clock-geometry）与导出 SVG 三端复用，服务端 resvg 与前端 canvas 渲染同一算法，保证所见即所得
- **契约宽容解析**：parseState 任意输入不抛错，clamp 非法值，未知键忽略 → 天然向后兼容
- **分离模式**：Web/dist 可脱离 server，`?server=` 指向任意后端

### 实测发现的两个缺陷（已用脚本复现验证）

1. **撤销栈 off-by-one（严重）**
   `Web/src/state.ts` 的 `commit()` 在 mutation **之后**才 `undoStack.push(clone(this.state))`，
   导致栈顶恒等于当前状态。实测（mock localStorage 跑真实 Store 类）：
   - 创建两个钟后 undo 一次 → 钟数仍为 2（应为 1）
   - undo 两次 → 1（应为 0），第三次栈空
   - redo 一次 → 2（应为 1）
   - increment 后 undo，fill 不变（撤销完全失效）
   修复方向：在 mutation 之前压快照，或改成 `commit(prevSnapshot)` 传参。

2. **非 ?readonly 的玩家端不轮询**
   `main.ts:367` 仅 `if (urlReadonly) { pollState(...) }` 才启动轮询。
   玩家打开 GM 分享的 `?room=xxx`（不带 readonly）时，既不轮询也不推送，
   只有 bootstrapPull 拉一次 → 全程静态快照，必须手动刷新。
   README 承诺的"玩家零安装打开浏览器即看"实际需要 `?room=xxx&readonly` 才成立。

### 其他待改进点（未验证，代码审阅得出）

- `state.ts:143` updateClock clamp max 到 [1,10]，而契约 `types.ts:81` parseState clamp 到 [2,10]，
  不一致：本地设 max=1 推送后服务器变 2，刷新页面状态跳变
- 零测试覆盖，同步逻辑（乐观锁/冲突/重试）最容易出错却无保护，撤销 bug 即例证
- 密码在 meta.json 明文存、Bearer 明文传、CORS `*`，威胁模型是信任网络（README 已诚实说明）
- `serveStatic` 的 `startsWith(DIST_DIR)` 缺路径分隔符，理论上可匹配 `distevil` 之类前缀目录，
  但 URL 构造已规范化 `..`，实际难以利用，属纵深防御加固项
- 每次页面启动 bootstrapPull → replaceState → notify → 防抖推送，会把刚拉下的状态原样推回，
  version 白涨（无害但脏）

### 评价结论

设计层面相当成熟：分层干净、契约先行、取舍诚实、决策记录完整（README 决策记录一节尤其好）。
问题集中在"实现没跟上设计"——两个核心功能（撤销、玩家实时同步）都是最后一层代码的疏漏，
而非架构缺陷。建议：先修撤销栈 + 轮询条件，再补 5~10 行的最小测试。
