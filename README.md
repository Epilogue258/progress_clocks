# progress_clocks —— 跑团进度钟工具

在线进度钟管理工具：GM 建钟、点钟、发图，玩家零安装打开浏览器即看。支持线下（平板/投影）与线上（网团）两种跑团形态，配套 API 可接入 QQ Bot 等外部插件。

## 游戏背景：什么是进度钟（Progress Clock）

进度钟是 **Blades in the Dark**（《暗夜刀锋》）及其衍生 Forged in the Dark 系统的一套规则机制，用于在跑团中追踪"正在逼近的麻烦"和"长期进行的努力"：

- 一个被分成若干段的圆（常见 **4 / 6 / 8 格**，问题越复杂格数越多）
- 每当角色掷骰部分成功或失败、产生后果时，GM 按后果程度**填充 1–3 格**
- 填满即触发对应事件：警报响起、守卫开始追捕、目标逃跑、革命爆发……

**关键规则**：

- **钟是障碍而非方法**——为潜入做的钟应叫"内部巡逻"而非"偷偷绕过警卫"；玩家可以用各种方法克服它
- **追踪进度而非决定进度**——钟是仪表盘，显示速度，不决定速度；GM 随时可按叙事调整
- **常用变体**：
  - **危险钟**：警戒度、追捕者接近、怀疑增长（填满 = 危险降临）
  - **竞争钟**：两个相反的钟对顶（"逃跑" vs "围堵"，先填满者胜）
  - **连锁钟**：填满后解锁新钟（"防御" → "脆弱"）
  - **任务钟**：倒计时，填满 = 任务取消或变化
  - **拉锯钟**：可填充也可清除（"革命！"、地盘争夺）
  - **长期项目**：8 格起步，多阶段，玩家改变世界的手段
  - **派系钟**：世界在玩家身后自行运转

本项目忠实实现这套机制：任意等分、点击填充、类型自由（程序不区分类型——那是叙事，不是状态）。

## 项目背景：为什么做成 Web

**起源**：面团跑团时 GM 用平板/投影管理多个进度钟（玩家围观同一屏幕）；网团时 GM 在电脑上操作、玩家各自设备查看。需要一个"零安装、即开即用、可同步"的进度钟。

**形态决策**：

| 形态               | 用途                | 理由                                                                 |
| ---------------- | ----------------- | ------------------------------------------------------------------ |
| **Web 应用**（主）    | 线上 GM 主控 + 玩家只读查看 | 玩家零安装，任何设备浏览器打开即用；未登录 GM 即为只读，并自动 5s 轮询；`?readonly` 连「连接与登录」入口一并隐藏 |
| **Apk**（待做）      | 线下平板主控            | 离线可用（线下无网），本地优先                                                    |
| **server + API** | 状态同步 + 图片导出       | JSON 契约统一三端；导出图可发群；外部插件（QQ Bot）可直接读写                               |

**网团场景**：跑团进行中，Bot 收到 `/clock 2/4 穿过守卫` → 注册/更新进度钟 → `/clock show` → 发送进度钟全景图到群里。API 只提供原语（读/写状态、导出图片），命令解析在 Bot 侧，灵活演进。

**技术栈**：TypeScript 全栈（Node 24 原生运行 TS，零编译步骤）、零框架（Web 手写 DOM + SVG）、唯一依赖 `@resvg/resvg-js`（服务端 SVG→PNG）。

**代码在哪**：最主要的文件是 `Web/src/ui.ts`（全部渲染与手势），其余都是围绕它的工具文件
——`main.ts` 编排同步与交互、`state.ts` 管状态与撤销栈、`api.ts` 封装 HTTP，`server/` 只是个可选的同步端。
行数每次改动都在变，不在此记录。



## 架构：GitHub 模型

```
本地工作副本（localStorage / 本地 JSON）          server（GitHub）
┌───────────────────────────┐                ┌───────────────────────┐
│ Web 前端（GM 主控/玩家只读） │  push / pull   │ data/rooms/<房间>/     │
│ QQ Bot / 手写脚本          │ ◄────────────► │   state.json          │
│ （每个端都本地持有一份 JSON） │  HTTP JSON 契约 │   meta.json（双密码）   │
└───────────────────────────┘                └───────────────────────┘
```

- **房间 = 仓库**：**新建远端房间从空开始**——服务器建空仓库、本地画布同步置空，不继承当前内容；
  加入房间 = pull 覆盖本地（本地数据不是权威，丢了无所谓）；
  GM 的改动自动推送到当前远端房间（防抖 500ms）；把本地草稿整体搬进远端房间用
  **「提交本地房间」**（本地房间里选目标、远端房间里选草稿，目标/来源二选一，force push 覆盖）。
  本地房间与远端房间已彻底分离，见下方「目标架构」
- **一个房间 = 一次团**：房间名即团名（支持中文/@/空格，如「龙与地下城@咖啡的房间」），状态按房间隔离，各房间独立乐观锁
- **双密码 = 读写锁**：加入密码（玩家只读，可空 = 公开房间）+ GM 密码（写凭证，必填 ≥6 位）；跑团本质是用外部通讯工具（QQ 等）同步这两把锁
- **分离模式**：Web 与 server 完全解耦——`Web/dist` 放任意静态托管，`?server=` 指向任一后端；同源托管时零配置。  
  （双击 `file://` 打开目前**不行**：`dist/index.html` 用 ES module，浏览器在 `file://` 下按 CORS 拦掉，见 `TODO-bcb78b27`）
- **同步**：GM 变更 → 防抖 500ms 全量 JSON 推送（乐观锁 version）；**未持有写凭证的一端** 5s 轮询（GM 端自身靠推送，不轮询）；启动拉取失败 5s 自动重试（server 重启后前端自动恢复）
- **冲突**：409 → 拉最新替换本地（丢包重做模式，桌游场景足够）；「写锁持有者发疯」只能靠推送前撤销 + 重建数据，工具无法阻止
- **安全边界**：房间名白名单防目录穿越（排除 / \ 与 Windows 保留字符）；1MB 请求体上限（超限回 413，不断开连接）；无 SQL 无注入面；version 伪造需写凭证，仅影响游戏数据

```
common/（共享层：契约/几何/导出 SVG）
  ├── Web/   GM 主控 + 玩家只读（同一应用两种角色）
  └── server/  多房间 JSON 持久化 + 导出图 API + Web 静态托管
```

## 目标架构：本地房间与远端房间分离（已实现）

> 这一节最初是设计稿，如今核心已落地：local 房间与 remote 房间彻底隔离、
> 「另存为本地」离线逃生舱、push 默认覆盖乐观锁、启动即本地工作区。
> 仍待补的缺口集中在「当前实现与目标形态的差距」一节与待办清单里。

### 初衷

玩家应当能在本地任意使用：不联网、不装 server、不连任何域名，也能建钟、点钟、导出。  
server 扮演的是 **GitHub** 的角色——一个可选的远端，用来跨设备同步和分享，  
而不是使用本工具的前提。换句话说：没有 server，工具应当功能完整，只是不能同步。

### 五条规则

1. **房间分两类，完全隔离**
   - **local 房间**：只活在本机，永远可编辑，永不发起网络请求
   - **remote 房间**：指向某台 server 上的房间；无写凭证时是只读镜像  
     二者不共用一份状态。「本地改动」对 local 房间而言就是终点，  
     对 remote 房间只是待推送的暂存。
2. **不维护「我是否在线」这个状态**  
   push 始终带上 GM 密码：密码不对服务端回 401，连不上就是网络异常——  
   两者由响应区分，客户端不需要预先知道自己在不在线。  
   所谓「掉线」不是一个需要被维护的状态，它只是客户端在服务器明确拒绝后  
   清掉已存密码这一动作的表象。  
   界面上的连接状态完全由**最近一次请求结果**（轮询 / 推送 / 启动拉取）推导（`reachable` / `degraded` / `down`），  
   不做独立探活。详见下方「同步协议」。
3. **「另存为本地」是断网时的逃生舱**  
   连接状态落到 `down`（轮询连续失败 3 次，见「断线的三阶段」）后，
   把除「另存为本地」以外的编辑入口置灰。  
   点下去把当前 remote 房间的内容落成一份 local 房间，  
   用户得以继续工作，而不是对着一张点不动的图发呆。  
   本地重名自动顺延为 `room_name(2)`（取第一个空位，不是无脑 +1）。  
   存下来的 local 房间记住 `origin: { server, room }`，恢复网络后可一键 push 回去。  
   **入口位置**：常驻顶栏「更多（⋯）」菜单，在线状态下随时可点——它不是「只有断网才有的功能」，  
   想把远端房间抓一份下来离线改，任何时候都合理。  
   写操作被置灰之后，要不要再在顶栏给它一个显眼入口，待定。
4. **push 默认覆盖乐观锁**  
   push 是用户主动发起的操作，等同于 Git 的 force push：请求体不带 `version`，服务端直接写入。  
   服务端已经支持——`POST /api/room/<name>/state` 的请求体里不带 `version` 即为强制覆盖，  
   **无需改服务端**。  
   `version` 由此从「锁」降级为「指示器」：仍用于判断远端是否领先于本地基线，  
   但不再拦住用户明确发起的写入。
5. **启动时不再强制进入远端房间**  
   打开页面就是本地工作区。进哪个 remote 房间是用户的选择，不是启动的前置条件。

### 同步协议：凭证随请求走，状态由响应推导

每个请求自带凭证，客户端只根据响应决定下一步，不预先判断自己在不在网：

| 请求        | 带什么                 | 401 的含义        | 网络异常的含义 |
| --------- | ------------------- | -------------- | ------- |
| 轮询 `GET`  | `joinPwd`（空 = 公开房间） | 加入密码不对，这房间你看不了 | 没问出结果   |
| 推送 `POST` | `gmPwd`             | GM 密码不对，你写不了   | 没问出结果   |

同一个 401 在两种请求里含义不同，客户端必须按请求类型分流。  
GM 完全可能持有正确的 `joinPwd` 和过期的 `gmPwd`——这时应当降级为只读并提示重输 GM 密码，  
而不是把整个房间的凭证清掉。

**401 与超时绝不能合并处理**：401 是服务器明确否定，可以清凭证并弹重输；  
超时是没问出结果，凭证必须原样保留，下次再试。

### 轮询结果的处理

| 结果          | 处理                                         |
| ----------- | ------------------------------------------ |
| 成功，版本相同     | 什么都不做                                      |
| 成功，版本不同     | 本地不 dirty → 采用远端；本地 dirty → 先 push，成功后同步基线 |
| 超时 / 网络异常   | 见下方「断线的三阶段」                                |
| `404` 房间不存在 | 提示「房间已不存在」并退出房间，不要无限重试                     |

前三条是日常路径，第四条容易被漏掉：GM 在 A 设备删了房间，B 设备的轮询就会撞上它。

四条容易漏掉的约束：

- **版本相同必须跳过。** `store.replaceState()` 会清空撤销栈并把「当前钟」选中态置空  
  （`state.ts` 的 `replaceState`）。此前实现无条件每 5s 替换一次，  
  等于每 5 秒清一次只读端的选中态——已修（回调先比对 `version`，相同直接 return）。  
  比对 `version` 不只是省一次渲染，更是避免这个副作用。
- **覆盖的前提是本地不 dirty。** 覆盖不可撤销（`replaceState` 清栈），  
  所以本地有未推送改动时绝不能被覆盖，必须先 push——与轮询回调里 `if (dirty) return` 一致。
- **置灰只针对写操作。** 保留一切不写契约数据的功能：视图切换、深浅模式、搜索过滤、  
  快捷键说明、导出图、另存为本地、连接与登录、退出房间。  
  置灰：新建、删除、填充/清除、钟设置、拖动排序。  
  撤销/重做看本地是否 dirty——有未推送改动时保留（它操作的是本地内容），否则置灰。
- **恢复要有可见反馈。** 静默恢复等于没恢复——用户不知道什么时候能继续编辑。

### 断线的三阶段

> 已实现。连接状态（`reachable` / `degraded` / `down`）由请求结果（轮询 / 推送 / 启动拉取）推导，不做独立探活；
> 本地房间与空白工作区不联网，恒 `reachable`，不参与本状态机。

1. **重试中**——首次连线失败**先静默补一次快速重试**：不提示、不置灰。
   局域网抖动、服务器重启的空档，大多在这一次里就过去了，为它弹提示只是噪音。
   补这一次仍然失败，才进「重试中」：置灰全部写操作，顶栏下方出「网络异常，正在重试」横幅，按轮询间隔继续。
2. **离线**（进入「重试中」后再连续失败 3 次）——横幅换成离线面板文案，
   写操作保持置灰，引导「更多 → 另存为本地」把内容落成一份本地房间继续跑团，而不是干等网络恢复。
3. **等待恢复**——轮询间隔逐步拉长 `5s → 10s → 20s → 40s`，上限 `60s`；
   横幅自带手动「重试」按钮，点了立刻发一次请求并把退避重置回起点。
   任一请求成功即解除置灰、关掉横幅，给一次可见的「已重新连接」反馈。

置灰只针对写操作：新建、删除、填充/清除、钟设置、拖动排序、提交本地房间；撤销/重做
按撤销栈保留（本地暂存仍可撤销）；导出 PNG、另存为本地、连接与登录、退出房间、深浅切换、
搜索、快捷键说明一律保留。轮询撞 401（加入密码错）不停留在退避里——直接停轮询并弹连接弹窗重输。

退避是必要的：房间已删或服务器已下线时，固定 5s 打下去只是空转。
手动按钮覆盖另一种情况——用户明明知道网络已经好了，不想等退避慢慢涨回去。

### 并发假设：多个客户端，一个作者

**假设**：GM 同时用 Bot、Web、手机管理同一个房间。所谓「并发」是这些客户端之间的时间差，  
不是两个意图相左的作者在抢同一份数据。最典型的场景是 GM 用 Bot 提交后立刻在 Web 上手动改——  
本人清楚改动目的，所以最后写入者胜是正确的。

**推论**：

- 不需要 diff / merge / CRDT，也不需要冲突解决界面
- 不需要「状态已在别处更新」这类打断式提示：GM 知道自己在改什么，弹窗只会碍事
- 唯一的安全网是撤销栈，因此**任何自动覆盖都不能在用户不知情时清掉它**  
  ——这正是上面「版本相同跳过」与「dirty 不被覆盖」两条约束的由来
- 服务端 409 能力保留：客户端 push 不带 `version` 后不再触发 409，  
  但第三方客户端（Bot）仍可能带 `version`，服务端不该为此改行为

### 为什么「拉取冲突」这项功能压根不该存在

没有写权限的玩家遇到冲突能做什么？不能改云端，只剩两条路：退出房间，或放弃本地改动。  
两条都是死路，所以那个确认对话框不该出现。冲突被规则 1 和 2 消化掉了：

- local 房间不联网，无从冲突
- remote 房间无写凭证 = 只读镜像，本地不存在「待推送的改动」，也就无从冲突
- remote 房间有写凭证 = 唯一合理的推送者，此时走规则 4 的覆盖语义

## 快速开始

```bash
# 1. 构建 Web 前端（产物 Web/dist 由 server 托管）
cd Web && npm install && npm run build

# 2. 启动 server（自动读 server/.env 里的 GM_KEY；没有则复制 .env.example）
cd ../server && npm install && npm start
# 打开 http://localhost:2333 （?demo 查看示例钟，?readonly 为玩家模式）
```

连接与登录：顶栏 `⋯` →「连接与登录」打开连接弹窗，服务器地址与凭证**一次提交**——填 `server/.env` 中的 `GM_KEY`（房间模式为建房间时设的 GM 密码），点「连接」即可。  
已登录时密钥框留空表示保持当前凭证，只换服务器（旧凭证会对着新服务器复验一次）。登录成功后顶栏出现撤销 / 重做 / 新建。  
**服务器地址只在这里改**——房间弹窗里不再提供该输入框，只显示当前连的是哪台。  
应用内按 `?` 可查看全部快捷键。

| 方法     | 路径                                     | 说明                                                                               |
| ------ | -------------------------------------- | -------------------------------------------------------------------------------- |

| GET    | `/api/auth-check`                      | GM 密钥验证                                                                          |
| GET    | `/api/export.png` / `.svg`             | 整张导出图（QQ Bot 直接下载发群）                                                             |
| GET    | `/api/rooms`                           | 房间列表（公开）                                                                         |
| POST   | `/api/rooms`                           | 新建房间（body: name + joinPwd + gmPwd；joinPwd 玩家只读可空 = 公开房间，gmPwd 写凭证必填 ≥6 位；重名 409） |
| GET    | `/api/room/<name>/state`               | 房间状态（需加入密码；公开房间免密）                                                               |
| POST   | `/api/room/<name>/state`               | 房间全量保存（需 GM 密码 + 乐观锁）                                                            |
| GET    | `/api/room/<name>/export.png` / `.svg` | 房间导出图（需加入密码；公开房间免密）                                                              |
| GET    | `/api/room/<name>/auth-check`          | GM 密码验证（写权限确认）                                                                   |
| DELETE | `/api/room/<name>`                     | 删除房间（需 GM 密码；不可恢复）                                                               |
| PATCH   | `/api/room/<name>`                     | 修改房间密码（需 GM 密码；body `{ joinPwd?, gmPwd? }` 只改传了的字段，gmPwd 须 ≥6 位）             |
| POST   | `/api/room/<name>/rename`              | 重命名房间（需 GM 密码；body `{ name }`，内容与密码原样保留，旧名立即 404——玩家需换新仓库）              |
| GET    | `/*`                                   | Web 静态托管                                                                         |

写接口（POST）的请求体上限 1MB，超限返回 413 并带上明确原因（不断开连接，客户端可据此判断是重试还是数据有问题）。

写外部插件（如 QQ Bot）前先跑 `python server/api-check.py`（详见 server/README.md）：默认只读、  
可直接对线上服务器跑；`--full` 才改数据，且在自建临时房间内做完即删，不碰默认房间和已有房间。  
想抄一份「命令 → 调 API」的参考实现，看 `server/example_bot.py`——无框架、可被任意框架 import（详见 server/README.md）。

## 统一 JSON 契约（SchemaVersion 1，定义在 common/types.ts）

```json
{
  "schemaVersion": 1,
  "version": 3,
  "clocks": {
    "1720000000000-a1b2": {
      "id": "1720000000000-a1b2",
      "name": "斯特朗福德宅邸警戒",
      "max": 4,
      "fill": 3,
      "color": "#e74c3c",
      "linkTo": "1720000000001-c3d4"
    }
  }
}
```

- `version`：乐观锁版本号，每次服务器写入 +1
- 扩展规则：新增字段可选，旧版本忽略未知键，天然向后兼容
- 边界：`fill` clamp 到 `[0, max]`，`max` clamp 到 `[2, 10]`，`linkTo` 指向不存在 id 时忽略。  
  边界常量 `CLOCK_MIN_SEGMENTS` / `CLOCK_MAX_SEGMENTS` 与 `clampInt()` 都定义在  
  `common/types.ts`，服务端解析与前端输入共用同一份，避免两端各写一份后漂移  
  （曾经前端写下界 1、服务端写 2，导致本地设 1 格推送后被改成 2 格，刷新跳变）
- **显示顺序不属于契约**：钟的排列顺序只存在本机 localStorage，  
  服务器、导出图、外部插件都不感知，因此契约里没有也不该有这个字段

- SVG 画钟：披萨饼式清晰接缝、填充动画、网格/列表双视图

  本地 `+` 新建本地房间（草稿工作区）。已取得凭证的远端房间挂标签——有 GM 密码 =「可编辑」、

  选中房间自动收起，比横向滚动条好操作得多
- **房间**（GitHub 模型）：顶栏房间名按钮或侧边栏进入——加入 = pull 房间状态（只读），
  新建 = **从空开始**（不继承当前画布，内容手动 push 上传）；
  双密码：加入密码（玩家只读，可空 = 公开房间）+ GM 密码（写凭证，必填 ≥6 位）；
  玩家不知 GM 密码则只读，GM 改动后玩家轮询同步；

  唯一例外是侧边栏已知房间一键切换——缓存条目自带服务器地址，切过去就必须连地址一起换。
  顶栏房间名按钮弹「房间管理」：**改名**（本地房间本地迁移槽、远端房间走 rename API，
  内容与密码原样保留、旧名立即 404——玩家缓存旧分享链接需换新仓库）、**改密码**（访问密码 /
  GM 密码，留空不更改）、**删除房间**（不可恢复）、**退出房间**（回到本地空白工作区，
  远端房间保留在服务器上）与**保存 / 取消**。本地房间无密码字段，只有改名 / 删除 / 退出 / 保存。
- **顶栏**：高频操作（撤销 / 重做 / 新建）留在顶栏，低频收进 `⋯` 菜单——
  连接与登录、退出房间、**另存为本地**（把当前远端房间落成本地快照，断网逃生舱）、
  **提交本地房间**（本地草稿 → 远端 force push；本地房间里选目标、远端房间里选草稿）、导出 PNG、
  深浅切换、快捷键说明。玩家模式只剩 4 个按钮
- **分离模式**：`Web/dist` 可脱离 server 单独部署到任意静态托管  
  （双击 `file://` 目前不行，见 `TODO-bcb78b27`），  
  通过 `?server=http://IP:2333` URL 参数或连接弹窗（顶栏 `⋯`）里的服务器地址栏指向**任意**后端（一百个服务器连任一，切换时重拉状态）；  
  同源托管（默认）时无需任何配置，行为与原先完全一致

## 决策记录

- **单写者精神：多个客户端，一个作者**：GM 同时用 Bot、Web、手机管同一个房间，
  「并发」是这些客户端之间的时间差，不是两个意图相左的作者在抢数据。因此最后写入者胜是对的，
  不需要 diff / merge / CRDT，也不需要冲突解决界面。推论是：唯一的安全网是撤销栈，
  任何自动覆盖都不能在用户不知情时清掉它。这是架构红线，扩展时勿破坏
  （`version` 因此从「锁」降级为「指示器」，见下）
- **不维护「我是否在线」这个状态**：每个请求自带凭证，客户端只按响应决定下一步——
  密码不对是 401，连不上是网络异常，两者由响应区分，无需预先探活。
  界面上的连接状态完全由最近一次请求结果（轮询 / 推送 / 启动拉取）推导。
  所谓「掉线」不是需要维护的状态，只是服务器明确拒绝后清掉已存密码这一动作的表象
- **401 与超时必须分开**：401 是服务器明确否定该凭证，可以清掉并提示重输；
  超时是没问出结果，凭证原样保留。合成一个布尔会让一次网络抖动永久删掉用户存好的密码
- **server 是可选的远端，不是使用前提**：玩家的初衷是本地任意使用——不联网、不装 server
  也能建钟点钟，server 扮演 GitHub 的角色只负责跨设备同步与分享。
  因此「能不能编辑」与「能不能推送」必须是两件事（下一条）。
  实现见[目标架构：本地房间与远端房间分离](#目标架构本地房间与远端房间分离已实现)
- **`readonly` 与 `canPush` 必须拆开**：没有 GM 权限最多意味着不能 push，不意味着不能改。
  现已拆为 `canEdit()`（本地/空白工作区永远可编辑；远端房间需 GM 凭证）与
  `canPush()`（只有远端房间且持写凭证才同步），离线打开远端房间不再「什么都不能点」
- **push 默认覆盖乐观锁**：push 是主动操作，等同 force push，请求体不带 `version`，
  服务端直接写入。服务端早已支持，无需改动。
  `version` 保留但降级为指示器：只用来判断远端是否领先于本地基线，不再拦用户明确发起的写入
- **版本相同就不做 `replaceState`**：`replaceState()` 会清空撤销栈并把「当前钟」选中态置空。
  无条件每 5s 替换一次，等于每 5 秒清一次只读端的选中态——比对 `version` 不只是省一次渲染
- **覆盖的前提是本地不 dirty**：覆盖不可撤销（`replaceState` 清栈），
  所以本地有未推送改动时绝不能被远端盖掉，必须先 push
- **断线提示要慢一拍**：首次连线失败先静默补一次快速重试，仍失败才提示并置灰。
  网络抖动与服务器重启的空档大多在这一次里就过去了；一失败就弹窗，
  是把实现细节当成了用户需要知道的事。补的这一次不计入离线判定的失败次数
- **不给无写权限者设计冲突处理**：没有写权限的玩家遇到冲突，能做的只有退出房间或放弃本地，
  两条都是死路。冲突应由「local 房间不联网 + remote 无凭证即只读」在源头消化，
  而不是弹一个选哪条死路的对话框
- **房间替代「多场景」**：契约方案 A（clock 加 group 字段）被房间模型取代——一个房间 = 一次团，状态按房间隔离更彻底，无需契约扩展
- **双密码**：单密码（读写同锁）让玩家拿到加入密码即可写，不符合「玩家只读」；拆分为读锁（joinPwd）/ 写锁（gmPwd ≥6 位）
- **轮询而非 WebSocket**：变更频率低（几分钟一次），5s 轮询足够且零依赖；要推送再上 SSE
- **全量覆盖而非增量**：数据几 KB，全量 JSON 推送最简单可靠，无 diff/合并复杂度
- **程序不区分钟的类型**：危险/竞争/连锁等是叙事标签，机制只有"填充/清除"；连锁的 `linkTo` 已从路线图移除（实现复杂、收益微小），契约字段保留但无人使用
- **index.html no-cache**：入口页下发 `Cache-Control: no-cache`（assets 带 hash 可长缓存），避免浏览器缓存旧构建导致「页面不更新」
- **启动拉取失败自动重试**：bootstrapPull 5s 重试，server 重启/离线期间打开页面，恢复后前端自动同步
- **Firefox 放弃**：弹窗不显示经排查为浏览器扩展（KISS-Translator 等翻译插件改写 DOM）干扰，非代码问题；以 Edge/Chrome/移动端为准
- **MD5 被否**：哈希传输可重放、无解密可言；GM 密钥用环境变量明文 + HTTPS/信任网络
- **显示顺序不进契约**：顺序是本机的视图偏好，服务器/导出图/QQ Bot 都不关心，
  因此单独存一个 localStorage 键而不写进 `ClockState`，契约保持零改动；
  `store.subscribe` 回调带 `ChangeKind`（`data` / `order`），排序变更不触发推送
- **拖动把手而非「按住卡片拖」**：移动端的长按已被「打开设置」占用，
  两者抢同一段指针序列必然打架；把手自带 `touch-action: none`，从它起手也不会被浏览器当成滚动
- **输入类控件只在 change 落库**：滑条与取色器若监听 `input` 事件写 store，
  每一帧都会压一次撤销栈，撤销会被噪声淹没；只在松手 / 回车 / 失焦时提交
- **只缓存验证通过的 GM 密码**：「已知房间」里 GM 密码输错就不记，
  否则下次切换会被无声地当成只读玩家，比每次重输更难排查
- **请求体超限回 413 而非断开连接**：原先超限即 `req.destroy()`，客户端只看到
  `ECONNRESET`，无从判断该重试还是数据有问题；改为停止读取但保留连接把 413 发回去
- **服务器地址只留一个入口**：同一个配置两处可改，改了这边就忘了那边。
  房间弹窗里的服务器输入框撤掉换成只读说明，`enterRoom` 也不再顺带改 `API_BASE`
  ——进房间是换仓库，悄悄把服务器也换了只会让人困惑
- **异步结果不写 DOM，写 UiState**：`render()` 是全量重画，
  `await` 回来时手上的节点可能已是孤儿，错误提示写进去用户看不见。
  弹窗提示（`gmError` / `roomError`）和输入草稿（`roomDraft`）都落进状态跟着一起重画，
  重渲染由调用方在异步结束后统一触发一次
- **CSS 兜底规则不放会被单点覆盖的属性**：`.modal input:not(...)×5` 的特异性高达
  (0,6,1)，会把 `.fill-input` 这类单类覆盖项 (0,1,0) 打穿。
  需要被覆盖的属性（如 `width`）一律写在同特异性的单类上，靠定义顺序取胜
